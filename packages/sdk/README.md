# @colosseum/sdk

The guard, which reads a transaction's bytes and refuses anything that is not the step the person approved, and the order executor the web and outside agents share. The design is `docs/vault/DESIGN-VAULT.md`, section 9 (the guard) and section 11 (the executor); what the web must hand the executor is in `apps/web/features/wallet/README.md`, "Before any product screen signs".

## Deployment files

The guard derives every address from a deployment, and takes one only as this package loaded it from the file committed for its network: `deployments/<network>.json`, with `"format": "guard-deployment/1"`. `local.example.json` shows a Solana and an EVM entry; `mock.json` is the mock's. `mainnet.json` is a placeholder (`"placeholder": true` with a `todo`): the loader refuses it until the real addresses are in and the mark and the note are out. Each asset carries its `decimals` (a mock entry its `cashDecimals`), the chain's own: a screen turns raw units into figures with them and never with a server's. `testnet.json` is written by the devnet set-up (`programs/tests/src/testnet/setup.ts`, `guardSolanaEntry`), and `deployment.test.ts` holds its decimals to `deployments/solana-devnet.json`, and the mock's to `packages/chain-mock`. The format stays `guard-deployment/1`: a file without decimals is refused, naming the field. A file is written in the pull request of the deploy to that network, and `pnpm --filter @colosseum/sdk tables` puts it into the package, frozen (`src/guard/generated/deployment-files.ts`); `scripts/tables.test.ts` fails while the two disagree. `deploymentsOf(network)` reads only those; `readDeploymentFile(content)` checks a file before it is committed and makes nothing the guard takes. The package's tests load deployments of their own through `test/deployments.ts`, swapped in with `vi.mock`. The test network's file and the transaction builders depend on this shape: a change to it is said in the pull request that makes it.

## For whoever builds the transactions

What the guard passes, so a builder knows before it builds (ADS-2 on Solana, ADE-2 on EVM):

- **Lookup tables (Solana).** Every account an instruction names in the interface (owner, vault, config, asset list, mints, token programs, the vault's and the person's token accounts, the router) must be one of the message's own keys. A named account loaded from a lookup table is refused, as is a program id. Only the trailing accounts may come from a table: a swap's route (`owner_swap`) and a withdrawal's transfer-hook accounts (`withdraw`). A platform table that holds Config, the asset list, the cash mint or the listed mints gives transactions the guard refuses.
- **Solana, besides the program's own instructions:** at most one compute unit limit and one unit price, nothing else of the compute-budget program, under the fee ceiling (0.005 SOL unless the deployment says otherwise; with no limit stated the price is counted on 1.4 million units). "Create this token account if it is missing" only for a token the step moves, paid by the person, for the vault's account of what comes in or the person's of what goes out, once each. No System or token-program instruction at the top level. One signer, the person, who pays the fee.
- **EVM:** a call, not a transaction: `to`, `value` `"0"`, `chainId`, the call data, and a nonce and gas limit if stated. Any other field is refused.
- **EVM deadlines.** `ownerSwap` and `createVaultAndBuy` carry a `deadline` (unix seconds) and the contracts refuse them after it. The guard passes one only if it is ahead of the guard's own clock and at most 30 minutes ahead (`MAX_EVM_DEADLINE_S`), so a builder sets it to the time of the build plus a few minutes, and a step signed and not sent stops being good. The other owner calls take none: none of them trades, so what they do does not depend on when they land, and the next transaction of the wallet takes the nonce a stale one holds (`accept_version` names the version the person reviewed).
- **EVM routes.** The guard reads the call data each trade hands its exchange (`Swap.data`) and holds it to the one route the builders write (`swapCalldata` in `packages/chain-evm/src/vault/routes.ts`): Universal Router's `execute(bytes,bytes[],uint256)` with the one command `V4_SWAP` and the actions `SWAP_EXACT_IN_SINGLE`, `SETTLE_ALL`, `TAKE_ALL`; the pool of the trade's two tokens, lower address first, swapped in the trade's direction, at the fee and tick spacing the deployment records for the traded asset (`assets[id].pool`: each asset has its own pool against the cash, and a trade of two assets, or of an asset with no pool recorded, has none) and the hooks it states for that router, with no hook data; the trade's `amountIn` in the swap and as the most to settle; the router's own minimums at zero, as built (the vault's `minOut` is the one that binds); and the trade's own deadline. Anything else is refused: `route` for the shape and the pool, `asset`, `amount`, `minimum` and `deadline` for the rest. A deployment's EVM entry states a route for every router under `routes`, by the router's address: `{ "kind": "universal-router-v4", "hooks" }` (hooks the zero address), or `{ "kind": "unread" }` for an exchange whose call data the guard does not read, such as a local mock router. A router with no route is refused by the loader, and `unread` is refused in mainnet's file. The pool is per asset, never per router: every asset but the cash states `"pool": { "fee", "tickSpacing" }` wherever a router's swaps are read, the cash states none, and a route that still names a fee for the whole chain is refused. On mainnet one stock's money sits at one fee and the next one's at another; a swap through any pool but the one recorded for its asset is refused as `route`. `test/fixtures/evm-route-vectors.json` holds the builder's own bytes; `route.test.ts` passes them and refuses each one-field change.
- **A creator's registry calls (Solana):** one `publish_recipe`, `update_recipe` or `cancel_pending`, with the creator as the one signer, the recipe account derived from the creator and the family id, the components and family id as the step has them, the text hash worked out by the guard from the text the step carries (`familyTextHash`, the encoding of `packages/basket/src/meta-hash.ts`, held to `fixtures/creator-limits/meta-hash.json` and to basket's own), and a fee cap and flags of zero. `buildPublishRecipe` and `buildCancelPending` of `chain-solana` build exactly that (`tests/solana-vault/registry-guard.test.ts`).
- **A creator's publish on the mock:** the mock's own `publish` operation, held to the step as the Solana check is: the creator, the family id, the text hash worked out by the guard, the assets and weights, no fee and no flags. The mock has one operation for a first version and the next, so `publish` and `update` are not told apart there; a cancel on the mock is refused as `unsupported`.
- **Minimums are held to equality** with what the review screen showed, so a rebuild at a new quote is refused until the person reviews again.

## Reading the chain

The executor signs an approved step once. A second signature needs the chain's word that the first can no longer land, through `chainReadOf({ solana, evm })`: one `RpcCall` per family, each to one node (`rpcAt(url)`), never the API and never a load-balanced URL, since a node that is behind and one that is ahead can each answer one of the reads. On Solana the node must have a transaction's blockhash before it is signed, and its block height then is kept with the signature; the first is gone once the finalized height is past that plus 150 blocks and a margin of 30, with no transaction of that signature on the chain. That last read searches the history, so the node must keep transaction history: one that keeps only recent slots would say not found for a transaction that landed. Whether a blockhash is valid at `finalized` proves nothing: the finalized block trails the tip. On a mock deployment no height is asked: the mock's transactions have no blockhash, and their lifetime is the mock's own clock. On EVM the first is gone once the finalized nonce has moved past it and the chain does not have it.

One run of an order at a time. Whoever calls `execute`, the web or an agent, holds a lock named for the order around it (in a browser `navigator.locks`, so tabs share it; in a process a mutex, or one worker per order): two runs over one `signed` store could each sign a step before either writes down what it signed.

A shared portfolio a screen follows is read the same way, from the screen's own node: `readSolanaRecipe(rpc, deployment, { creator, familyId })` reads the registry's account at the address the program derives from the two, with the cluster's clock, and answers the version in effect and the one that waits, each line's mint mapped to the deployment's asset (null for a token it does not list); an account that is not the program's recipe, or names another creator or family, throws. `familyIdOf(slug)` is the id of a new portfolio, the API's own rule (`packages/basket`), and `vaultOf(deployment, owner, basketId)` the vault a plan number names, as the guard derives it, so a screen can hold a vault's address and its plan number to each other before it names that number in a step.

## Tests

`python3 packages/sdk/scripts/mutate.py` removes the guard's and the executor's comparisons one at a time in a copy of the package and runs the tests that should notice; it exits 1 when one survives (`--check` only says each still applies). `test/bites.ts` runs each negative twice: the whole guard refuses it with the code of one check, and with that check taken out it passes. The switch that takes a check out, or reads against another interface, is `test/rules.ts`, which a test file puts in place of `src/guard/rules.ts` with `vi.mock`. It is not in the guard, and nothing the package builds imports from `test/` (`src/guard/rules.test.ts`).
