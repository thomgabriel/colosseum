## Retention of the hosted tables (Oct 16)

Thom, Oct 16: the hosted database moves from Supabase (871 MB, over the free plan's size and egress) to a free Neon project (1 GB a branch, aws-us-west-2); it keeps about the last four days of raw liquidity readings, older rows are archived to files on his Mac, and a daily job prunes. The windows are in one list, `scripts/ops/risk-retention.ts`, which the prune (`pnpm ops:prune-risk`), the archive (`pnpm ops:archive-risk`) and the move (`pnpm ops:move-db`) all read. Every row that leaves the database is in a file on the Mac. For every windowed table but one that file is the collector's own (pools, assets, evm/assets, lending, quotes and lp day files, `events.jsonl`, the lending reports under `~/.colosseum/hosted-risk`; append only, and no collector or job deletes them), which the import read the rows from; `scripts/ops/README.md` lists them. `risk_pool_flow` has none (the daily rewalk keeps only its last walk), so the move's archive and then the daily launchd job `com.colosseum.risk-prune` write its aged rows to `~/tenonfi-archive` before the prune, which never cuts it past the archive. The daily job reads about 5 MB a day out of Neon; `tests/ops-risk-retention.test.ts` fails on a risk table that is in neither list. A row is old when it is more than its window older than the earlier of now and the table's newest row, so a table whose collector stopped keeps its last window. **What a row stores (Oct 18, DB-STORAGE).** Neon's free plan stops writes at 1 GB, and the database stood at about 700 MB with these windows (pool snapshots 352 MB, lending snapshots 114, asset snapshots 80, pool flow 55, lending facts 20). The import now stores only what a reader uses, with no figure a page or an answer shows changed:

- A pool or asset curve is stored as `[notionalUsd, outUsd]` pairs in the collector's order, the two numbers every reader uses, exactly as the collector wrote them (`packSide`, `packages/risk/src/curve-store.ts`); `costPct`, `unfilledShare`, `poolsUsed` and the Robinhood Chain route detail stay in the collector's files. No number is rounded: the API returns figures derived from these unrounded (the heatmap's `medianCost`, the capacities), so a rounding would change an answer. A side the pairs cannot hold exactly (an outUsd absent, a notional not a number) is stored as written. Every reader takes both forms (`curvePairs`, `curveNotionalOut`, `curvePointAt` in `apps/api/src/history.ts`, `scripts/risk/curve-read.ts`, `sidePoints`), since older rows keep the object form until they age out.
- A pool side that a ten-minute run found as the pool's last stored curve is stored as JSON null; the hourly run's row keeps both curves. The heatmap reads a null side as the pool's previous curve, so each run still counts the pools it read (the ten-minute runs read tier A only, which the heatmap's best pool per run depends on, and a side simply left out would lose that). The prune cuts pool snapshots on the UTC hour (`hourAligned`, `scripts/ops/risk-retention.ts`), so the oldest row it keeps of a pool is from a full run and a null side never outlives the curve it repeats; a run with a null side whose curve is gone anyway (the full run missed that pool) is left out of the heatmap rather than counted without its best pool.
- A lending snapshot's `detail` keeps `symbol`, `debtSymbol`, `supplyApr` and `borrowApr`, the keys the lending report reads (on the newest row per account and kind); the whole row stays in the lending day file. The reconstructed `*_hourly` rows already stored keep their whole rows, since they are never cut.
- `risk_lending_facts` and `risk_lending_coverage` keep two days instead of four.
- `risk_pool_flow` is unchanged: its `method` and `source` (about 500 characters) repeat on every row, and storing them once would need a migration.
